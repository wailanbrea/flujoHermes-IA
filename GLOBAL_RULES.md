# Reglas globales

1. Una tarea verificable por vez.
2. Recuperación selectiva de archivos; nunca cargar repositorios completos.
3. Excluir dependencias, binarios, builds, logs grandes y backups.
4. Avisar al 75 % del contexto, compactar aproximadamente al 80 % y producir handoff
   antes del 90 %.
5. Registrar objetivo, alcance, comandos, resultado real, evidencia, riesgos y estado.
6. Detener una causa tras tres intentos fallidos y actualizar `docs/BLOCKER_REPORT.md`.
7. Mantener separación entre orquestación, inferencia, herramientas, validación y
   observabilidad.
8. Codex, Claude Code, Antigravity y OpenCode deben seguir
   `config/agent-governance.md`: Graphify primero, Hermes para la ejecución pesada y
   revisión independiente antes de integrar.
9. REGLA DE RECUPERACIÓN OBLIGATORIA: Cuando el usuario pregunte si recuerdas, creaste, trabajaste, modificaste, investigaste o hablaste sobre algo anteriormente: (1) No responder basándote únicamente en el contexto activo; (2) Consultar el registro de proyectos; (3) Consultar el registro de tareas; (4) Ejecutar session_search con al menos dos variantes relevantes; (5) Consultar la memoria persistente; (6) Consultar Graphify si se trata de un proyecto de código; (7) Verificar la existencia de la ruta o repositorio; (8) Indicar las fuentes encontradas; (9) Solo decir que no existe registro después de completar todas las búsquedas; (10) No ofrecer comenzar desde cero hasta comprobar que el trabajo anterior realmente no existe.
10. REGLA DE AUTOMATIZACIÓN DE NAVEGADOR Y PLAYWRIGHT: Cuando el usuario solicite abrir el navegador o usar Playwright, no dar excusas de entorno ni sugerir alternativas. Ejecutar directamente los scripts con Playwright (`npx playwright` / `python -m playwright`), extraer la información/capturas y entregar el reporte final de una vez.
11. REGLA DE ACCIÓN DIRECTA SIN META-RESPUESTAS EXCUSATORIAS: Realizar las acciones requeridas de forma autónoma sin emitir meta-respuestas explicativas ni preguntas de confirmación teóricas (como *"¿Quieres que te informe de cada paso o solo el reporte final?"*). Ejecutar la tarea completamente y entregar los resultados directos.
12. REGLA DE PRESUPUESTO DE TOKENS (IA LOCAL VS. IA CLOUD): El sistema de atomización profunda en 16 etapas (`RECEIVED` ➔ `DELIVERED`), DAG de tareas `T-001..T-025` y Repair Loop aplica únicamente a la IA Local (Hermes Brain / VRAM Local). Para IAs Cloud (Codex, Claude, Antigravity, OpenCode), aplicar un flujo directo y optimizado de 3 a 5 fases para preservar cuotas, reducir contexto y ahorrar costo de tokens en APIs cloud.
13. REGLA DE USO AUTÓNOMO Y ONBOARDING DE GRAPHIFY: Prohibido entrar en bucles de lectura o intentar peticiones HTTP sobre URLs de archivos `file:///`. El agente DEBE consultar `telemetry/runtime/project-catalog.json` (donde los 38 proyectos YA están 100% indexados) y entregar directamente la URL del Dashboard de TRAMA `http://127.0.0.1:4310` o el archivo `file:///C:/AI-Workspace/local-ai-orchestrator/graphify-out/graph.html` con las métricas del proyecto en 1 sola respuesta limpia.
14. REGLA DE LEVANTAMIENTO AUTÓNOMO DE SERVICIOS WEB Y XAMPP: Prohibido dar excusas o pedir pasos manuales al usuario. Detectar el stack y ejecutar autónomamente: PHP Vanilla (`php -S 127.0.0.1:8080`), Laravel (`php artisan serve`), Python (`python manage.py runserver` / `uvicorn`), Node/Vite (`npm run dev` / `dist`), validar la respuesta HTTP con `Invoke-WebRequest` y entregar la URL activa de inmediato. PROHIBIDO entregar URLs no compiladas o carpetas con espacios como `http://localhost/Nombre Con Espacios/` o sugerir abrir paneles de XAMPP manualmente. La ÚNICA URL válida para cualquier web es `http://127.0.0.1:[Puerto]` (`8080`, `8000`, `5173`).
15. REGLA DE AUTOMATIZACIÓN DE GIT COMMIT Y PUSH: Prohibido pedir al usuario realizar commits o pushes de forma manual. Tras verificar cambios o a solicitud del usuario, ejecutar de forma autónoma `git status`, `git add .`, `git commit -m "tipo(alcance): descripción"` y `git push origin main`, entregando el hash corto del commit y la confirmación del respaldo remoto.
16. REGLA DE PROHIBICIÓN DE SIMULACIÓN DE PRUEBAS EN TEXTO: Prohibido redactar falsos reportes o fingir la ejecución de pruebas (ej. "Paso 1: Exitoso... Paso 3: Error") sin haber ejecutado realmente los scripts en la terminal. Todo resultado debe derivarse de ejecuciones reales con evidencia verificable.
17. REGLA DE APLICACIÓN INMEDIATA DE PARCHES Y CORRECCIONES: Prohibido preguntar "¿Quieres que aplique el parche de código?" o pedir confirmación teórica al detectar una falla. Modificar el código de inmediato, validar la solución y entregar el reporte con la corrección ya aplicada.
